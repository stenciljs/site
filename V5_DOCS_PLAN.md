## Vision

Two audiences, one site:
1. **New users** get a seamless line from "never heard of Stencil" to "shipped a component library" — install → `stencil init` wizard → author a component → configure output → test → document → deploy/integrate.
2. **Existing users** can find one specific fact fast, without wading through onboarding prose.

This is not just "update the docs for renamed APIs." Structure, writing quality, and example freshness are equally in scope.

Standing steers from John (these apply to every page):

- **Shadow DOM is one option, not the default.** The footgun reputation belongs to shadow DOM; plenty of developers avoid web components because of it. `encapsulation` defaults to `'none'`; shadow is opt-in. "Non-shadow" means `scoped` and `none` together. `none` + native [`@scope`](https://developer.mozilla.org/en-US/docs/Web/CSS/@scope) is the modern-browser alternative to `scoped` (Baseline "newly available" as of Firefox 146, Dec 2025 - say so honestly).
- **Four component archetypes, presented as equally first-class** (`concepts/component-archetypes.md`): CSS-only (a real compiler feature, `components/css-only.md`) → progressively-enhanced (an emergent pattern, not a named feature) → custom element without shadow → custom element with shadow. Every archetype is typed and documented by the same static-analysis pipeline - decorators for a class, JSDoc tags for a CSS-only file.
- **Design systems first, apps second.** `www`, prerendering/SSG, service workers, and routing stay fully documented but get proportionally less emphasis than authoring, output targets, and testing. When `guides/` gets subgrouped (§4.6), the service-workers cluster is explicitly app-oriented, not equal billing.
- **Writing quality bar:** the feedback memories for this project (no em dashes, no contrastive "X, not Y" constructions, no meta-commentary, introduce before using, cut tutorial asides, don't over-specify how-to conditions). Read them before writing or reviewing prose.

## 1. Versioning & branch strategy — DONE

Implemented in `site/docusaurus.config.js` (2026-08-25):

```js
lastVersion: 'v4.43',
versions: {
  current: { label: 'v5 (Preview)', path: 'v5', badge: true, banner: 'unreleased' },
  'v4.43': { label: 'v4.43', banner: 'none' },
},
```

- **Default (un-prefixed) site view stays on stable `v4.43`.** Most visitors aren't beta testers; they shouldn't land on preview docs by accident.
- **`docs/` (the "current"/editable slot) is now v5's exclusively**, all the way through beta → RC → GA. It shows as a real, permanent, linkable `/v5/` entry in the version dropdown — not `/next/` — so beta/RC testers can be pointed at it directly. Label is stage-agnostic ("Preview") so it doesn't need edits as the prerelease stage changes.
- **Branch model:** both `stencil-site` and `stenciljs` are checked out on a `v5` branch, diverged from `main`. `main` (stencil-site) is the live site and keeps cutting ordinary `v4.x` doc versions independently — it already reflects the engine repo's `main`, which shipped v4.44.1 on 2026-08-21 while `v5` sat 362 commits ahead. **Intent is to merge this branch into `main` ASAP**, not hold it back until GA, so beta/RC users have real docs to refer to while trying prereleases.
- **Consequence of merging early:** once merged, `docs/` no longer doubles as "next v4.x." Any v4.x-only doc fix needed after the merge must be hand-applied directly inside the frozen `versioned_docs/version-v4.43/` snapshot (or a hand-created `version-v4.44/` folder + matching `versions.json`/`versioned_sidebars` entry) — versioned snapshots are static files, fully editable without `docs:version`. There's no "next" slot for v4 once v5 owns `docs/`.
- **Before merging:** check whether `main`'s already-shipped v4.44.1 needs a corresponding `v4.44` docs version cut first (not yet investigated — flag next time this comes up).
- **At GA:** cut `docusaurus docs:version v5.0`, then flip `lastVersion` to `'v5.0'`. `docs/` reverts to being a genuine "next" slot again (v5.1, v6, ...).

## 1.1 Verified: `stencil init` vs `stencil add`, and current CLI state (2026-08-25)

Confirmed by reading `packages/cli/src/{run.ts,task-init.ts,task-add.ts}` on the local `stenciljs` `v5` branch and running the built CLI directly in a scratch directory (build artifacts were already present, current version `5.0.0-alpha.35-dev.1787665438.64571f0` — no fresh build needed for this check):

- **`stencil init` and `stencil add` are two distinct, real CLI tasks**, not one merged entry point — `run.ts` dispatches `'add'` → `taskAdd()` and `'init'` → `taskInit()` separately. Docs should reference both by name, not just `init`: `stencil init` scaffolds a new project; `stencil add` adds capabilities (testing, styling, framework output targets, etc.) to an existing one. (`V5_PLANNING.md` has one stale line claiming "no `stencil add` command needed" that predates this — don't trust that line.)
- **Monorepo detection is real**: `detectWorkspaceRoot()` walks up from the working directory looking for `pnpm-workspace.yaml` or a `package.json` with a `workspaces` array, and both tasks use it to install/scaffold into the right workspace package rather than assuming a single-package repo root.
- **Neither task supports non-interactive/CI mode yet** — both print "Running in CI - non-interactive mode is not yet supported" and exit when `CI` env is set. Worth a callout in docs (can't script `stencil init`/`stencil add` in a CI pipeline today) and worth re-checking before final docs ship in case this lands before GA.
- **Package-manager-prefixed entry point** (`npm init stencil@5`, `pnpm create stencil@5`, `yarn create stencil@5`, `bun create stencil@5`) is the intended primary docs framing, not `npx stencil init` — per `V5_PLANNING.md`'s `create-stencil` shim design, these resolve to the `create-stencil` npm package. **The `@5` (or `@next`/`@alpha`) suffix matters for the whole preview window**: plain `npm create stencil` keeps resolving to the current stable line until `create-stencil` publishes a v5-compatible dist-tag. Docs must show the explicit version suffix throughout beta/RC and only drop it once v5 is GA/`latest`.
- ~~Bug found, not yet reported to engineering: `stencil --help` on the current alpha build still advertises `stencil test --spec --e2e`...~~ **Fixed 2026-08-26** (commit `1ba37c0da`, "chore: update breaking changes and cli --help (#6850)"). Re-ran `--help` to confirm: the stale `stencil test` text is gone, and the output is now accurate and worth treating as the source of truth for `config/cli.md`'s rewrite:

  ```
  Init: Scaffold a new project, or add capabilities to an existing one.
    $ stencil init

  Add: Install and configure an integration (framework wrapper, output target, etc).
    $ stencil add [package]

  Generate: Bootstrap a new component.
    $ stencil generate [name] or stencil g [name]

  Build: Build components for development or production.
    $ stencil build [--dev] [--watch] [--serve] [--prerender] [--debug]
      --dev / --watch / --serve (requires --watch) / --prerender / --docs
      --ssr ............. Build a server-side-rendering bundle
      --config / --maxWorkers / --no-cache / --stats / --log / --ci / --debug

  Serve: Start the dev-server without building or watching.
    $ stencil serve [--root] [--no-open]

  Docs: Generate configured docs output targets.
    $ stencil docs [--docsJson]

  Prerender: Prerender a hydrate app script against the source index.html.
    $ stencil prerender <hydrate-app-path>

  Migrate: Codemod a project for the latest major version breaking changes.
    $ stencil migrate [--dry-run]

  Info / Version / Telemetry: (not captured - verify before documenting)
  ```

  Notable, not yet reflected in the plan's earlier `config/cli.md` notes: `--ssr`, `--maxWorkers`, `--no-cache`, and `--ci` are build flags not previously called out; `serve`, `docs`, and `prerender` are now standalone top-level tasks (not just `build` flags) — `config/cli.md`'s rewrite should document all three as their own commands. `stencil init`'s own description now explicitly says it also covers "add capabilities to an existing one," while `stencil add [package]` reads as the more targeted, package-scoped shortcut — don't over-assert the exact division of labor between the two without a live run of both; note the apparent overlap and verify by actually running each before writing the final doc section.

**Method note:** this is the working pattern going forward for CLI/build-behavior claims — read the source, then actually run the built CLI in a scratch directory, rather than trusting planning-doc prose alone (which, per the `stencil add` line above, can itself be stale). Not every fact needs a live run (type-level changes, config renames confirmed by reading the compiler source are usually enough), but anything about *runtime/CLI behavior* specifically should get a quick real check before it goes into a doc.

## 2. Proposed information architecture

Four independent audits converged on the same core critique: the current top-level list (`introduction`, `components`, `framework-integration`, `static-site-generation`, `config`, `output-targets`, `documentation-generation`, `guides`, `core`, `testing`, `reference`, plus two orphaned loose files) reads as accretion, not a designed journey. Framework integration (a late-journey "consume it" concern) outranks config and output targets (early/mid-journey "build it" concerns). `core/` vs `config/` is a naming collision only an insider would parse. SSR is split across a whole rival top-level category (`static-site-generation/`) instead of living with its actual output target.

### New top-level structure

| Pos | Category | Purpose |
|---|---|---|
| 1 | `getting-started/` | Install → `stencil init` wizard (new project + add-capabilities modes) → `stencil generate` → first component. Tutorial mode, replaces most of today's `introduction/`. |
| 2 | `components/` | Author a component: decorators, `encapsulation`, styling, JSX, signals, reactive controllers. |
| 3 | `config/` | `stencil.config.ts` reference: CLI flags, dev server, `compat` (renamed from `extras`), plugins. |
| 4 | `output-targets/` | One page per target: `loader-bundle`, `standalone`, `www`, `ssr` (+ nested `ssr/<language>.md` family for `ssr-wasm`), new first-class `collection`/`types`/`global-style`/`assets`, and the `docs-*` targets folded in from today's `documentation-generation/`. |
| 5 | `framework-integration/` | Consuming components from Angular/React/Vue/Ember/vanilla JS — a "consume it" concern, moved later than today's position 3. |
| 6 | `testing/` | `@stencil/vitest` + `@stencil/playwright` only. |
| 7 | `guides/` | How-to catch-all for what doesn't fit the linear journey — needs internal subgroups (see §5). |
| 8 | `concepts/` (new) | Explanation mode: what/why Stencil, design systems, rendering-strategy trade-offs. Absorbs the "why" half of today's FAQ. |
| 9 | `reference/` | Pure fact-lookup only: support policy, versioning policy, CLI/compiler/dev-server embedding API (merged from today's `core/`), `build-variables.md` (finally given a home), telemetry CLI facts. |
| — | Community (manual) | Unchanged. |
| — | Legal (manual) | Privacy policy + telemetry opt-out prose (CLI facts move to `reference/`). |

**Cross-cutting: `stencil init`/`stencil add` should be the "easy way" callout on many pages, not just `getting-started/`.** Since third-party packages participate in both via a `stencil.wizard` export, most "how do I set up X" questions now have a one-line wizard answer worth surfacing right at the top of the relevant page, before the manual steps: framework output targets (`framework-integration/*`, once `@stencil/react-output-target` etc. ship a wizard), Storybook (`guides/storybook.md`), Signals (once that config flag has a wizard path), testing (`testing/vitest`, `testing/playwright` — already wizard-integrated per `KNOWN_INTEGRATIONS`), and linting, once/if a lint package ships one. Add "the easy way: `stencil add <package>`" callouts as each of these gets rewritten, not as a separate pass.

**Why `ssr-wasm` nests under `output-targets/ssr/` rather than getting its own top-level category:** it's one output target's per-language onboarding family, and this mirrors the already-proven `framework-integration/{angular,react,vue}.md` and `testing/{vitest,playwright}/` pattern — scales to a dozen languages without a second reorg.

## 6. Live/embedded code examples

**Retracted 2026-08-26: `playground-elements` is the wrong default tool here, per John.** Original reasoning (2026-08-25) treated this like Lit's docs problem - Lit is mostly a thin runtime over native web components, so "run the source in a sandboxed browser iframe" (what `playground-elements` does) is a reasonably faithful stand-in for "show what the reader wrote." Stencil is different in a way that matters: its whole pitch versus Lit is that it's a **compiler** - decorators, JSX, `styleUrl`/`globalStyleUrl`, `encapsulation` are all resolved and transformed at build time, not just executed as-authored. `playground-elements` can only execute pre-built code in a sandbox; it can't run Stencil's compiler, so every demo built on it would have to hide the compile step behind a black box - exactly the "magic" a compiler-first project most needs to make legible, not hide. John: "giving people the full context is imperative."

**Also confirmed while investigating alternatives: running Stencil's own compiler live, client-side, isn't available.** Old search hits (a stale `compiler-api.md` v3 doc, a years-old JSFiddle, in-source JSDoc on `transpile()`/`transpileSync()` claiming browser support) pointed at genuine but obsolete capability - "In Browser Compilation Support Removed" is a real, documented v4.0.0 breaking change (`BREAKING_CHANGES.md`: "Prior to Stencil v4.0.0, components could be compiled from TSX to JS in the browser... has been removed from Stencil. At this time, there is no replacement functionality."). I should have cross-checked this against v5.0.0-section context I'd already read earlier in this same session before treating the old signal as current - noted as a gap in the verification habit, not just a one-off miss.

**Two candidate directions, from John, neither decided - needs a technical POC before committing to either:**
1. **`@stencil/unplugin`** (the new v5 universal bundler plugin for Vite/Rollup/webpack/rspack/bun, see `V5_PLANNING.md`) **running inside a real in-browser Node/bundler runtime.** [StackBlitz WebContainers](https://developer.stackblitz.com/platform/api/javascript-sdk) (Node.js compiled to WASM, runs fully client-side, verified 2026-08-26 via WebSearch as a strong fit specifically for "Node-shaped" tooling like Vite) is the concretely-identified option - spin up a real Vite + `@stencil/unplugin` project, edit source, get a real recompile with real HMR, genuinely showing the actual transformation because it *is* the actual transformation. Heavier than a sandboxed iframe (a real, if fast-booting, Node environment) and couples to StackBlitz's own embed/IDE shape.
2. **A custom-built playground UI** using [Sandpack](https://sandpack.codesandbox.io/) (CodeSandbox's embeddable editor/preview framework, built for exactly this "build your own dev-tool UI" use case) as the interface layer, backed by a real in-browser Node runtime (CodeSandbox's own "Nodebox," or another WebContainer-class runtime) for actual compilation underneath. More engineering investment, but buys full control over the UI shape - e.g. a Svelte-REPL-style layout (source / compiled output / live preview panes side by side), which is the right mental model here since Svelte faces the identical "compiler, not just runtime" documentation problem and solves it exactly this way. Nodebox's current capabilities weren't verified beyond generic vendor-comparison sources during this session - genuinely needs hands-on investigation, not more reading.

**Still valid, unaffected by the above:**
- **"Open a full working project" CTAs** (e.g., after the `stencil init` walkthrough, or a complete framework-integration recipe): StackBlitz SDK embeds - this may end up serving both the "full project" and "inline example" cases with one tool if direction 1 above pans out.
- **`ssr-wasm` polyglot examples (PHP/Java/Go/Rust/...): do not attempt live-in-browser execution.** Neither WebContainers nor Sandpack/Nodebox can run non-Node runtimes. Plan for verified, tested static code samples per language plus a linked minimal starter repo - that's the honest, deliverable version of "live examples" for this family.

**First concrete use case (tool-agnostic), from John:** `components/styling.md`'s "Choosing an Encapsulation Strategy" section is the flagship candidate for whichever direction the POC lands on - three near-identical demo components differing only in `encapsulation` (`shadow`/`scoped`/`none`), same CSS selector applied to all three, shown live side by side so the reader *sees* the isolation difference instead of reading three parallel prose descriptions of it. The page already has an inline `<!-- TODO(live-demo): ... -->` HTML comment marking the exact insertion point (see `components/styling.md`, "Choosing an Encapsulation Strategy" section) - update that comment once a direction is chosen, it currently still names `playground-elements` specifically.

**Considered and rejected, 2026-08-26: a second live demo for global styling** (co-location via `globalStyleUrl`, `@import "stencil-component-globals"` merging multiple components' CSS, multiple `global-style` outputs). This is almost entirely a **build-time** transformation regardless of which tool gets chosen above for the encapsulation case - direction 1 (`@stencil/unplugin` in a real Node runtime) *could* actually show this live since it runs the real compiler, but the payoff is much smaller than the encapsulation case (multi-file CSS merging is less visually dramatic than live shadow-DOM isolation) and it's not worth scoping into the same POC. The one genuinely runtime-visible piece of the global-styles story (a global stylesheet's `:host(my-button)` rule reaching a live shadow root once `inject: 'client'` is set) is exactly the `inject` detail already deferred out of `components/styling.md` to the future `output-targets/global-style.md` page (§5 item 7) - revisit whether it deserves a live demo once that page and the playground direction both exist.

**Added 2026-08-26, from John directly (not surfaced by the audit), corrected/expanded after a follow-up clarification — read this version, not the edit summary in git log for the first pass:**

The footgun reputation belongs to **shadow DOM**, not the alternative to it — plenty of developers avoid web components generally because shadow DOM's isolation (style, focus, event retargeting) is more than they want or understand. Stencil's actual position is that shadow DOM is *one* option, not *the* option, and the docs currently don't say so. Today's only real mention of the alternative (`styling.md`'s Scoped CSS section) frames it defensively ("does not, however, prevent styles from the light DOM from seeping into your component") instead of as a deliberate, well-supported, first-class choice.

Terminology, precisely: **"non-shadow"** covers both `encapsulation: { type: 'scoped' }` and `encapsulation: { type: 'none' }`. Within non-shadow, there are now two ways to get real style scoping:
- `type: 'scoped'` — Stencil's own mechanism (data-attribute-based CSS scoping + light-DOM patches for slot-like behavior), broad browser compatibility.
- `type: 'none'` **paired with the native CSS [`@scope`](https://developer.mozilla.org/en-US/docs/Web/CSS/@scope) at-rule** — the new "evergreen" alternative for modern-browser-only projects: real scoping with zero Stencil runtime mechanism, in place of `scoped`. (Verified 2026-08-26: `@scope` reached Baseline "Newly available" as of Firefox 146, Dec 2025; also Chrome 118+, Safari 17.4+, Edge 118+. Real, current, but "newly available" — be honest that some users may still be on pre-146 Firefox rather than claiming universal support.)

**The bigger point, beyond shadow-vs-non-shadow:** Stencil v5 has a first-class story for more than one component archetype, and the docs should present this as a spectrum, not corner cases:
- **Traditional JS-driven components** — the classic model, any encapsulation type, behavior lives in the class.
- **CSS-only components** — a custom element that's just a styled tag, no meaningful JS logic.
- **Progressively-enhanced components** — light-DOM/slotted content that's already meaningful before JS loads, with JS enhancing rather than creating the experience.

The claim tying it together: **no matter which archetype you pick, JS or no JS, your components stay fully typed and documented** — decorator-driven static analysis (`docs-json`, `docs-readme`, the CEM, `types-output-target`) doesn't care about encapsulation or runtime behavior, it reads the `@Component` class either way. And v5's new style co-location tools are what make the "before JS runs" and "after JS runs" states easy to manage together instead of as separate concerns: `@Component`'s new `globalStyleUrl`/`globalStyle` fields co-locate document-level styles with the component (collected at build time, injected wherever `@import "stencil-globals"` appears in a global stylesheet — works for every encapsulation type), and the `@import "stencil-hydrate"` placeholder injects static FOUC-prevention CSS at build time (the pre-upgrade state) instead of relying on the loader's dynamic `<style>` tag. Both verified directly against `stenciljs/V5_PLANNING.md`'s New Features section.
